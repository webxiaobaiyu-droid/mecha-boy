# GitHub《重装机兵》相关开源项目调研

调研日期：2026-08-03
目标：从不同语言的公开实现中提炼可用于《荒原引擎》的系统设计与工程方法，不复制商业游戏素材、ROM 数据或许可证不兼容的源码。

## 1. 结论先行

当前项目不缺一条能跑通的主线，也不需要更换引擎或重写渲染层。最值得吸收的是其他项目对“内容如何被表达”的处理：

1. **优先建设数据驱动事件系统**：把当前 `world.ts` 中按剧情名硬编码的分支，逐步替换为可验证的事件指令。它直接决定后续城镇、支线和多结局能否低成本生产。
2. **把遭遇从单怪随机升级为生态表**：采用“区域 -> 敌群 -> 权重 -> 数量范围 -> 特殊组合”的结构，支持同一区域的层次和稀有遭遇。
3. **让战车部件形成战术选择**：补充炮弹容量、攻击范围（单体/一组/全体）、部件兼容槽、部件小破/大破，而不是继续只增加攻击力档位。
4. **让敌人靠行为差异而非纯数值区分**：引入类型、属性抗性、行动模式、分裂、死亡爆炸、再生和 Boss 阶段。
5. **内容反馈系统放在核心玩法之后**：怪物图鉴、物品图鉴、任务日志、稀有精英、周目继承都值得做，但不应先于事件工具链和正式地图管线。

## 3. 做得好的地方

### 3.1 内容事件成为独立协议

`Finb/MMX` 的事件图将内容拆为触发、条件、变量写入、对话、等待和传送节点。`MetalMaxRe` 又区分进入地图后自动执行的动态脚本与调查后执行的静态脚本，并为脚本动作保存代码、参数长度、格式、跳转位置和说明。

这比在世界系统里增加更多 `switch (storyId)` 更适合长期制作内容。对本项目而言，不需要复制可视化节点编辑器；先建立一套可序列化、可测试的事件指令即可：

```ts
type EventCommand =
  | { type: 'say'; dialogueId: string }
  | { type: 'choice'; prompt: string; options: EventChoice[] }
  | { type: 'if'; condition: EventCondition; then: EventCommand[]; else?: EventCommand[] }
  | { type: 'set'; key: string; value: boolean | number | string }
  | { type: 'add'; key: string; amount: number }
  | { type: 'giveItem'; itemId: string; amount: number }
  | { type: 'startBattle'; encounterId: string }
  | { type: 'teleport'; mapId: string; x: number; y: number }
  | { type: 'mutateMap'; mutationId: string; active: boolean }
  | { type: 'wait'; ms: number }
```

事件应支持 `interact`、`enterTile`、`enterMap`、`battleWon` 和 `auto` 触发类型，并允许用优先级选择第一个满足条件的分支。这样 NPC 能根据任务状态换对白，门和机关能改变地图，Boss 战后也不必再在战斗系统里写特定名称判断。

### 3.2 遭遇表表达“生态”，不是单次抽签

`MetalMaxRe` 的怪物概率模型同时保存：

- 每个普通敌人或特殊敌群的权重；
- 每类敌人的最小/最大数量；
- 特殊怪物组合；
- 怪物组合在普通地图和世界地图上的分布。

可在本项目中落成：

```ts
interface EncounterTable {
  id: string
  noEncounterWeight: number
  entries: Array<{
    groupId: string
    weight: number
    min: number
    max: number
    conditions?: EventCondition[]
  }>
}
```

它能自然支持稀有金属怪、夜间敌群、天气限定敌群、赏金首附近的护卫组合，以及剧情前后不同的区域生态。测试应验证权重非负、总权重大于零、敌群引用存在、数量范围合法。

### 3.3 战车部件有更多设计维度

`6ag/MM1` 和 `MetalMaxRe` 的战车模型共同体现了几个比单纯攻击成长更有价值的维度：

- 主炮弹仓与弹药消耗；
- 单体、一组、全体三档攻击范围；
- 武器可装入哪些炮穴，而不是只看武器名称类别；
- 底盘的炮穴配置、改造上限和改造阶梯；
- 发动机可形成升级链；
- 部件存在正常、小破、大破状态；
- 玩家自有战车与出租战车是两套所有权模型。

建议先做最能改变决策的四项：`ammo/maxAmmo`、`targeting`、`compatibleSlots`、`condition`。部件损坏应由战斗结果产生，并在战车工房修复。炮弹补给则让主炮与 S-E 成为需要规划的高价值资源，副炮保留无限弹药定位。

不建议马上做完整底盘打孔、租车系统或十几级改造链；它们需要新的 UI、经济平衡和教程，适合事件系统稳定后再做。

### 3.4 敌人需要特征规则

`MetalMaxRe` 的怪物数据覆盖坦克、仿生、电子类型，以及装甲、命中、回避、攻击次数、攻击模式、抗性、分裂、死亡爆炸和每回合恢复。`zzgl` 的精英敌人则通过概率把属性、经验、金钱和掉落倍率附加到普通敌人上。

本项目应优先建立通用规则，而不是在 `battle.ts` 中继续按 Boss ID 写分支：

```ts
interface EnemyTrait {
  type: 'resistance' | 'regen' | 'split' | 'deathBurst' | 'enrage' | 'phase'
  // 各类型使用带判别字段的独立参数
}
```

第一批可做：

1. `machine / bio / human` 敌人类型与武器克制；
2. 火焰、爆炸、电击三类伤害与抗性；
3. 再生、召援、死亡爆炸三个可组合特征；
4. Boss 按 HP 阈值切阶段并替换行动表。

精英词缀适合后续区域重复探索，但必须使用明确的词缀行为，例如“装甲化”“自爆”“高速”，不能只把所有数值乘 `1.2`。

### 3.5 地图会因事件改变

`MetalMaxRe` 的世界地图互动事件保存事件条件以及真假状态下的两组图块，可表达涨潮/退潮一类地形变化。它还把入口、出口、边界传送、宝藏、随机调查点、电梯和传送目的地分别建模。

本项目已有清晰的地图语义层，适合增加 `mutations`：每个 mutation 描述要替换的图块、碰撞、触发器和前景对象。典型用法包括：

- 修好桥后永久开放捷径；
- 炸开洞口后改变碰撞与场景外观；
- 城镇遭袭前后替换 NPC 与服务状态；
- 开闸导致水位变化，开放一条路线并封闭另一条；
- Boss 死亡后在场景中留下残骸和调查点。

所有变体只保存 mutation ID 到存档，不把整张变更后的地图写入存档。

### 3.6 完整内容需要反馈与回访理由

`zzgl` 的公共事件和启用插件显示，它在主线之外加入了怪物/物品图鉴、任务日志、随机宝箱、多个结局、昼夜天气、乘降、键位映射、战后结算和周目继承。最值得提炼的是“玩家做过什么，游戏要持续反馈”：

- 悬赏档案记录发现、击破、领奖三个状态；
- 怪物图鉴只显示已遭遇或已击破的信息；
- 任务日志给出当前目标和已完成步骤，不直接显示未发现支线；
- 新周目只继承明确白名单，例如图鉴、外观和少量收藏，不继承剧情开关；
- 分章节发布时，每章必须有独立问题、高潮和状态收束，不能只在任意位置截断。

## 5. 集成路线

### P0：内容生产底座

1. 定义事件指令、条件和执行上下文；执行器不直接依赖 Vue 或 Canvas，只通过现有 `GameApi` 完成副作用。
2. 迁移 `story_rado_father`、`story_masaru_mecha` 和一个门/宝箱事件，保留旧入口用于兼容。
3. 为事件数据增加静态校验：引用、不可达分支、无限跳转、缺少对白、无效地图坐标。
4. 把麦镇的独立事件作为首个完整样本，验证对话、入队、给物品、战斗、传送和地图变体。

验收标准：增加一条支线只改 `src/game/data`，不改 `world.ts`、`store.ts` 或 Vue 组件。

### P1：战斗与战车深度

1. 建立敌群与权重遭遇表。
2. 建立伤害类型、敌人类型、抗性和行动表。
3. 增加战车炮弹、部件损坏与战车工房修复。
4. 用一个普通敌群、一个精英变体和一个两阶段 Boss 做纵切。

验收标准：同一攻击对三种敌人产生可解释的不同结果；主炮弹药与部件损坏能跨战斗保存并在服务点恢复。

### P2：世界反馈

1. 地图 mutation 与永久捷径。
2. 通用任务日志、怪物图鉴和物品图鉴。
3. 昼夜/天气只作为遭遇与事件条件接入，视觉表现后补。
4. 正式结局完成后再加入白名单式周目继承。

## 6. 明确不建议集成的内容

- **不改成 Unity、Godot、Babylon ECS 或原生 C++**：现有 Vue + TypeScript 状态层已有测试和完整纵切，重写不会解决内容生产问题。
- **不引入 RPG Maker 式插件堆栈**：`zzgl` 的功能量可作产品参考，但大量插件互相覆写原型，许可证也各不相同。
- **不复制 ROM 解包数据、经典地图、对白、敌人名称或图像**：即使工具源码开源，商业游戏内容本身也不因此变为可用素材。
- **不优先做联机、抽卡、装备打孔、赛马小游戏或在线活动**：这些功能会分散核心赏金循环和正式内容管线。
- **不依据仓库星数直接选实现**：多个高相关仓库只有空壳或编辑工具，必须按实际源码核验。

## 7. 落地状态与下一步

首个 P0 任务已完成：项目已有最小事件运行时，并迁移了拉多父亲开局和麦镇机械师入队事件。当前文件边界如下：

```text
src/game/
  data/events.ts          事件定义与内容
  systems/events.ts       纯规则执行器
  types.ts                EventCommand / EventCondition / EventDefinition
test/
  events.test.ts          分支、引用校验与对话后恢复执行测试
```

运行时支持条件分支、flag 写入、队员招募、音效、内联/引用对白，以及在对话关闭后继续剩余指令。`WorldSystem.runStory()` 先执行数据事件，未迁移事件继续走旧逻辑，因此存档和其余 Boss 流程不受影响。

下一张开发票应是：**建立敌群与权重遭遇表，并只迁移拉多、麦镇两个区域**。战车炮弹单独放到后续迭代，避免一次改动同时触碰世界、战斗、商店和存档四个系统。
